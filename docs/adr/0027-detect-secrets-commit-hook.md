# ADR-0027: Block new secrets with detect-secrets, at commit time and in CI

**Status**: Accepted
**Date**: 2026-09-20

## Context

The repository already forbids committing secrets, state and build output
(`AGENTS.md` rule 6), but nothing enforced the "secrets" part — a committed
AWS key or API token is only noticed if a human spots it in review, at which
point the secret is already in git history and must be rotated and purged.
The edge signer (ADR-0019) and the deploy pipeline deal in real credentials,
so the closer a secret gets to `main`, the more damage a leak does.

Yelp `detect-secrets` fits this repository's baseline workflow: the current
tree is scanned once, reviewed findings are recorded in `.secrets.baseline`,
and afterwards only *new* secrets fail a check. The two existing baseline
entries are reviewed false positives, not live credentials:

- `packages/core/src/jev/infrastructure/http-jev-client.test.ts` — the
  literal `"test-key"` stub API key in the fetch test.
- `packages/edge-signer/src/signer.test.ts` — well-known public test
  vectors: the empty-string and `"abc"` SHA-256 digests and the official AWS
  SigV4 `get-vanilla` suite strings, which are high-entropy by construction.

## Decision Drivers

- **Must be green at the moment it lands.** A gate that starts failing
  teaches everyone to bypass it.
- **Must not depend on code changing to re-check.** Like the audit gate
  (ADR-0011), a hook alone is bypassed by `--no-verify` and never runs on
  fork pull requests.
- **Local and CI must evaluate the same thing.** If the hook and the gate
  use different plugin sets, contributors chase failures they cannot
  reproduce.
- **One new tool, not a new toolchain.** Contributors already need Bun,
  Terraform and Docker; whatever scans secrets should be a single install.

## Considered Options

### Which scanner

**Option A: Yelp `detect-secrets` with a committed `.secrets.baseline`.**
- **Pros**: Baseline model means the gate starts green without touching
  test fixtures; `pragma: allowlist secret` handles future false positives
  inline; hook scans only staged lines, so it runs in well under a second.
- **Cons**: Requires Python and a `pip install` on every contributor
  machine — the one new tool this decision adds.

**Option B: Gitleaks (single Go binary).**
- **Pros**: No baseline to maintain; stronger default rules; no Python.
- **Cons**: Still a new binary to install locally; noisier on test vectors
  unless a config allowlist is maintained, which is the same maintenance in
  a different file.

**Option C: Hand-rolled `bun` regex script, zero new installs.**
- **Pros**: Runs everywhere Bun does; no new dependency category.
- **Cons**: Secret detection is an arms race; a local regex list is weaker
  than either maintained tool and becomes this repository's to maintain.

### Where to run it

**Option A: `lefthook` pre-commit only**, scanning staged files.
- **Pros**: Fastest feedback, before the commit exists.
- **Cons**: Skipped by `--no-verify`; never runs on fork PRs.

**Option B: CI gate only**, scanning all tracked files.
- **Pros**: Cannot be bypassed.
- **Cons**: Feedback arrives after a push instead of before a commit.

**Option C: Both — staged scan in the hook, full-tree scan in CI.**
- **Pros**: Fast local signal plus an unbypassable backstop; mirrors the
  audit gate (ADR-0011).
- **Cons**: Two places to keep in sync (mitigated below by pinning).

## Decision

**Option A** for the scanner, **Option C** for where it runs.

1. `.secrets.baseline` is generated by `detect-secrets scan` (version
   `1.5.0`) and committed. Its two finding groups are the reviewed test
   vectors above.
2. `lefthook.yml` runs `detect-secrets-hook --baseline .secrets.baseline`
   on staged files at `pre-commit`.
3. `gates.yml` runs the same hook over all tracked files. CI installs
   `detect-secrets==1.5.0` — pinned to the version in the baseline — so
   both sides evaluate the same plugin set. Bump the pin and regenerate the
   baseline together when upgrading.
4. False positives are marked inline (`# pragma: allowlist secret` or
   `// pragma: allowlist nextline secret`), not by editing the baseline by
   hand. Regenerating the baseline uses a temp file so the read is not
   truncated by the shell redirect:
   `detect-secrets scan --baseline .secrets.baseline > .secrets.baseline.new
   && mv .secrets.baseline.new .secrets.baseline`.
5. Local setup is one command: `pip install detect-secrets==1.5.0`.

## Consequences

### Positive

- A new secret is blocked before the commit exists locally, and blocked
  again in CI even if the hook was skipped or never installed.
- The gate starts green: existing findings are recorded and reviewed, not
  suppressed invisibly.
- Contributors without the tool get a clear `detect-secrets-hook: command
  not found` failure pointing at the one install command, not a silent pass.

### Negative

- Python is now a contributor prerequisite alongside Bun — the first
  non-Bun runtime the guardrails require.
- The version pin is manual: if CI and a contributor's local install drift,
  results can differ. The baseline's `version` field and the install
  comment in both configs are the only reminder; there is no lockfile for
  the Python side.
- Baseline scanners only see what their plugins know. A novel secret shape
  can still pass; this gate raises the bar, it does not remove review.

### Risks and mitigations

- *Risk*: A real secret is already in history and got baselined sight
  unseen. *Mitigation*: The two baseline groups were read line by line
  during this change (test stub key, public hash vectors); `detect-secrets
  audit .secrets.baseline` remains available for future reviewers to
  re-label them.
- *Risk*: The hook is skipped repo-wide via `--no-verify` habit.
  *Mitigation*: The CI job is the actual enforcement; the hook is a preview
  of it — same split as ADR-0011.
